  - **立即 return**，不进入后续逻辑

#### control.py - `_start_target_download`:
- 开始时调用 `ui.hide_transfer_error()` 清除上次失败的错误提示

#### control.py - `_on_transfer_failed`:
- 新增 `ui.hide_transfer_error()` 调用

#### ui.py - 新增错误提示区域:

## 大磁盘文件列表超时 + 配置检测后无"下一步"按钮修复 (2026-08-03)

### Bug 1: D/E 盘 100+GB 小文件导致 /list API 超时

**根因**: `_handle_list` 用 `os.walk()` 遍历整个目录树 → 内存中构建完整 JSON → `_send_json` 一次性发送（含 `Content-Length`）。100+GB 小文件遍历需数分钟，客户端 30s 超时直接放弃。

**修复 (file_transfer.py)**:
- **服务端流式写入** (`_handle_list` 重写):
  - 不再构建完整文件列表内存后一次性发送
  - 边 `os.walk` 边逐条 `wfile.write()` 文件条目
  - 每 500 个文件 + 每个目录处理完都 `wfile.flush()`，保持连接活跃
  - 用 `Connection: close` 代替 `Content-Length`（流式传输，客户端读至连接关闭）
- **客户端超时提升**: `/list` 超时 30s → 300s
- **JSON 格式不变**: 客户端解析逻辑无需改动

### Bug 2: F 盘检测到配置文件后步骤 4 无"下一步"按钮

**根因**:
1. 配置文件检测到后，虽然 `set_button_next("normal")` 被调用，但"开始传输"按钮仍显示"连接中..."（disabled），UI 混乱
2. 点击"下一步"会直接跳转到步骤 5 而不使用检测到的配置（绕过配置选择）

**修复 (control.py)**:
- `_on_download_complete()`: 传输成功完成后调用 `ui.hide_start_button()` 隐藏"开始传输"按钮
- 无配置文件时: `hide_config_detect()` + `go_step(5)` 直接跳转
- 有配置文件时: `show_config_detect()` 显示检测框，"下一步"按钮正常启用
- `_on_next_step()`: 新增检查 — 步骤 4 接收端若已检测到配置，点击"下一步"自动调用 `_on_use_detected_config()`（等效于点击"使用此配置"）

## 配置导出后自动压缩上传到 Profile 服务器 (2026-08-03)

### 需求
- 配置导出成功后，自动压缩为 ZIP 并上传到 `http://ipcheck.gtmcl.com:3000/api/upload`
- 命名格式: `<COMPUTERNAME>_<YYYY-MM-DD>.zip` (如 `QDNB5098_2026-07-31.zip`)

### 实现 (config_transfer.py):
- 新增 `compress_and_upload_config(export_path, log_callback)`:
  - 步骤 1: `zipfile.ZipFile` 压缩导出文件夹 (ZIP_DEFLATED)
  - 步骤 2: `urllib.request` POST multipart/form-data 上传 ZIP
  - 返回 `(compress_ok, zip_path, upload_ok)` 三元组
- `_run_out_cmd()`: 新增 `HEADLESS=1` 环境变量，防止 out.cmd 重复压缩上传

### 实现 (control.py):
- `_on_export_done()`: 成功后按钮变为 "导出完成，正在压缩上传..." (disabled)，启动后台线程
- 新增 `_start_compress_upload()`: 后台线程调用 compress_and_upload_config
- 新增 `_on_upload_done()`: 主线程回调，根据结果更新按钮状态 (success/warning/danger)
- 三种结果状态:
  - 上传成功 → "导出并上传完成" (success)
  - 压缩成功/上传失败 → "压缩完成(上传失败)" (warning), ZIP 本地保留
  - 压缩失败 → "导出完成(压缩失败)" (danger)

## 上传未触发 + 校验 CSV UTF-16 编码修复 (2026-08-03)

### Bug 1: 部分导出失败时压缩上传被跳过 (根因)
`_export_config_builtin` 返回 `(fail_count == 0, export_root)`, 任一导出项失败(如 Chrome 未安装) → `success=False` → `_on_export_done` 中 `if success:` 守卫跳过 `_start_compress_upload`。

**修复 (control.py)**: 移除 `if success:` 守卫, 只要 `export_path` 非空就触发压缩上传。

### Bug 2: 后台线程直接操作 Tkinter Text 控件
`_start_compress_upload` 中 `log_callback=self._log_export` → 后台线程直接写 `log_text.insert()`/`log_text.config()`, 非主线程操作 Tk 不安全, daemon 线程可能静默崩溃, 按钮卡死在"正在压缩上传..."。

**修复 (control.py)**: `_log_safe(msg)` 通过 `self.ui.after(0, ...)` 回到主线程; `_run()` 加 try/except 兜底 → `_on_upload_error`。

### Bug 3: 校验 CSV UTF-8-sig 无法解码 UTF-16 LE 文件
报错: `'utf-8' codec can't decode bytes in position 0-1: invalid continuation byte`。
BOM `FF FE` (UTF-16 LE) 在 `utf-8-sig` 下无法解码, Windows PowerShell `Out-File -Encoding Unicode` 等工具生成的 CSV 默认 UTF-16 LE。

**修复 (verifier.py)**: 新增 `_detect_csv_encoding(csv_path)`:
- 读取文件头 4 字节, 检测 BOM: `FF FE` → `utf-16-le`, `FE FF` → `utf-16-be`, `EF BB BF` → `utf-8-sig`, 无 BOM → `utf-8`
- 替换所有 4 处硬编码 `encoding="utf-8-sig"` 读操作为动态检测编码
