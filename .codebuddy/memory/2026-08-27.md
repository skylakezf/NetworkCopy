## DHCP 致命 bug 修复 + 发现成功率提升 + 移除接收端网卡选择

### 1. 致命 bug：60 秒后点开始报「请先点击开启DHCP」
- 根因：`_start_target_download` 要求 DHCP 服务器 `is_running()`，但 `_dhcp_tick` 60 秒倒计时归零后已 `stop()`。源设备其实已拿到 IP（`_source_ip` 已设），不再需要 DHCP。
- 修复：允许继续的两种情况 —— ① 服务器仍在运行；② 服务器已停但 `_source_ip` 已设置（DHCP 分配完成）。从未点过「寻找」（`_use_dhcp=False`）才报错。

### 2. 提高 DHCP 发现成功率（4 处）
- `dhcp_server.py` 新增 `set_out_ips()` + `refresh_out_ips()`：APIPA 地址在服务器启动后才出现时，动态绑定新广播出口 socket（防多网卡/虚拟网卡下 OFFER/ACK 无出口）
- `_setup_target_dhcp`：启动 DHCP 前轮询等待 APIPA 地址（169.254.x.x，最多 20 秒）——刚插网线时 Windows 需约 15 秒探测才分配
- `_dhcp_tick`：每秒调用 `set_out_ips`+`refresh_out_ips` 动态刷新出口
- `_setup_source_network`：首次 renew 未命中后周期强制 renew 60 秒（每次 renew 触发 DISCOVER），提高「接收端 DHCP 后启动」场景命中率；仍以 APIPA 兜底

### 3. 移除接收端网卡选择逻辑（保留发送端）
- `_on_dhcp_button`：去掉 `_get_adapter_desc_from_auto()` 检查（启动时未插网线会导致无法发起寻找）
- `_setup_target_dhcp(adapter_desc)` → `_setup_target_dhcp()`：去掉参数与 `get_local_ip(adapter_desc)` 兜底
- `_configure_ip(adapter_desc, device_type)` → `_configure_ip(device_type)`；`_on_device_type_selected` 同步简化
- `_get_adapter_desc_from_auto` 仍保留（`_start_source_server` 源端手动 IP 模式 `_apply_manual_ip` 使用）

### 测试
- 8 套件全绿。TC-03c 曾因 fake_dhcp 模拟（仅设 `_use_dhcp=True`+running）未设 `_source_ip` 短暂失败，已将检查改为「`_source_ip` 或服务器运行中」两者之一即可，兼容测试模拟与真实场景。

## 传输期间全屏锁定「霸占全盘」（同日，用户需求）

### 实现（ui.py + control.py + file_transfer.py）
- **ui.py** 新增 `lock_screen()`/`_screen_lock_poll()`/`unlock_screen()`：`attributes("-fullscreen", True)` + `-topmost` + 拦截 `WM_DELETE_WINDOW`（禁 Alt+F4/X 关窗）+ 每 500ms 轮询 `focus_displayof()` 失焦即 `lift()+focus_force()` 抢回；unlock 恢复全屏/置顶/关闭协议并 `after_cancel`。幂等（`_screen_locked` 标志）。
- **control.py**：
  - 发送端 `_start_source_server` 启动后 `lock_screen()`，并 `after(2000, _poll_source_done)` 轮询检测接收端完成
  - 接收端 `_start_target_download` 启动后 `lock_screen()`
  - 解锁点：`_on_download_complete`（开头统一，覆盖成功/失败/断开）、`_on_transfer_failed`、`_on_network_lost_ui`；`shutdown` 兜底解锁 + 取消源端轮询
- **file_transfer.py**：FileServerHandler 新增类变量 `active_requests`/`ever_connected`/`last_activity`（do_GET/do_POST 记录，finally 递减）；FileServer 新增 `is_transfer_done(idle_seconds=15)` —— 曾有客户端 + 无活动请求 + 空闲超 15s → 判定接收端已完成。**原因**：发送端无完成回调（接收端校验报告上传到外部 Profile 服务器），只能靠空闲检测。
- 已知限制：Ctrl+Alt+Del 系统级无法屏蔽；多显示器时 `-fullscreen` 仅主屏。

## 发送端进度同步 + 完成后可正常关闭（同日，用户需求）

用户需求：①向发送端同步拷贝进度；②数据传输完成后发送端应用能正常关闭。

### 实现（新增 `/report` 上报通道，替代纯空闲检测）
- **file_transfer.py**：
  - FileServerHandler 新增 `POST /report` 端点（body JSON）：接收端上报进度/完成。`done` 时置 `transfer_done_flag`；`status_callback` 类变量在请求线程中回调 control。
  - FileServer 构造新增 `status_callback` 参数，start() 时注册；`is_transfer_done()` 改为**显式 done 标志优先 + idle 15s 兜底**。
  - 新增客户端函数 `post_report(host, port, auth_code, payload)`（HTTPS POST，复用 `_get_thread_connection` 连接池，失败静默）。
- **control.py（接收端）**：新增 `_report_to_source(payload)`（后台线程，host=`_last_source_ip or _source_ip`，auth=`_auth_code`）；`_progress` 闭包中**节流 1s** 上报 `{done:False, files_done/total, bytes_done/total, status}`；`_on_download_complete` 开头上报 `{done:True}`（成功/失败/断开统一）。
- **control.py（发送端）**：新增 `_on_source_report`（转主线程）→ `_handle_source_report`（progress → `_set_progress` 百分比 + `_set_status("[接收端] ...")`，覆盖传输页状态文字，红色验证码横幅 `tk_label_auth_code` 不受影响；done → `_source_mark_done`）；`_source_mark_done()`：`unlock_screen()` + 进度条 100 + 状态"接收端已完成拷贝，可安全关闭此窗口" + `_source_done_marked` 幂等防重。`_poll_source_done` 统一走 `_source_mark_done`。
- 发送端"正常关闭"根因：之前只靠 idle 检测，接收端校验阶段重试下载会不断刷新 `last_activity` 导致 15s 空闲窗口难出现 → 永不解锁 → X/Alt+F4 被 lock_screen 拦截 → 关不掉。done 上报从根本上解决。
