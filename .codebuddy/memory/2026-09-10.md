## 修复：传输时源端日志被"拒绝连接/读取握手头失败"刷屏（非故障）

### 现象
传输进行中，发送端（源端）日志每秒持续出现两条：
`[诊断] 收到新连接来自 ('169.254.x.x', 49xxx)` + `[诊断] 拒绝连接 ...: 读取握手头失败/超时: 客户端未发送数据 (连接已关闭)`；端口号连续递增。软件功能全部正常。

### 根因（跨模块隐式交互）
接收端 `control.py: _start_network_monitor` 的断网监控线程**每 1 秒**调用 `_host_reachable(ip)`，该函数用**裸 TCP** `socket.create_connection((ip, 9999))` 探活后立即 `close()`，**不做 TLS 握手、不发任何字节**。
源端 `file_transfer.py: ThreadingFileServer.get_request` 的 TLS 强制检查读到 `recv(MSG_PEEK) == b""` → 按"非法/握手失败"路径打印 2 条诊断日志。
注意：`control.py:1829` 处的一次性连接自检早已改成真实 TLS 握手探测（注释里也解释过这个坑），但**网络监控线程用的 `_host_reachable` 仍是裸 TCP**，是本次刷屏唯一来源。

### 修复（只改日志，不改任何拒绝/传输行为）
`file_transfer.py: ThreadingFileServer.get_request`
- 新增分支：`peek` 读到 0 字节即关闭 → 判定为"端口探活连接"，**静默丢弃、不打任何日志**（新增 `except ConnectionAbortedError: raise` 与显式 raise 区分于通用异常）。
- `[诊断] 收到新连接来自 {addr}` 从"accept 后立即打"改为"**确认读到客户端数据后**才打"，避免探活连接触发。
- 顺手去掉日志模板中重复的 `(连接已关闭)` 后缀。
- 真实客户端的日志（收到新连接 / TLS 握手成功 / 握手失败）行为不变；拒绝逻辑、异常类型（仍抛 OSError 子类保证 serve_forever 不崩）完全不变。
`control.py: _host_reachable` docstring 补充说明"本探测会被源端识别为探活连接并静默忽略"（跨模块契约）。

### 测试
- `tests/test_func.py`：`ServerFixture` 新增 `collect_logs=True` 可选收集日志；新增用例 **B3c**——用裸 TCP 连 3 次即关，断言日志中无"收到新连接/拒绝连接/读取握手头失败"，且随后 HTTPS `/ping` 仍 200（服务存活）。
- `run_tests.py --only func --only full_flow`：**51/51 通过**（func 35 + full_flow 16）。

### 遗留观察（未改）
`get_request` 读握手头超时为 30s，且该调用发生在服务主线程：若客户端连上后既不发数据也不关闭，服务端会最多 30 秒不接受新连接（探活连接立即 close，不会触发）。如将来遇到"传输莫名卡住"，可考虑把握手头超时改短（如 5s）。

## 修复：网线已连好后再点「寻找旧电脑」，源端获取 IP 极慢

### 现象
源端（发送端）已在等待/或早已启动，用户在接收端（目标设备）**后**点击「寻找旧电脑」启动 DHCP，源端要几十秒甚至更久才拿到 `169.254.100.2`。

### 根因（三处叠加，按影响排序）
1. **源端重试窗口太短且放弃后不再尝试**（`control.py: _setup_source_network`）：首次 20 秒 + 重试 60 秒共约 80 秒后彻底停止。用户若在这之后才启动接收端 DHCP，源端**再也不会发 DISCOVER** → 看起来"永远等不到"。
2. **重试时只 `renew` 不 `release`**：`IpRenewAddress` 是阻塞式 Win32 调用（无 DHCP 响应时可阻塞数十秒），且只 renew 时 Windows DHCP 客户端会停在指数退避（1/2/4/…/64 秒）里；更糟的是这个阻塞调用跑在主等待循环里，导致"每 10 秒观察一次"实际退化成每 60 秒一轮。**每轮先 `IpReleaseAddress` 会把客户端重置回 INIT 状态，使 renew 立即广播 DISCOVER**，这是关键。
3. **接收端 `dhcp_server.py: _handle_request` 无条件 ACK 客户端 option 50 请求的地址**：源端网卡若之前从其它 DHCP（办公网）拿过异网段租约，会以 INIT-REBOOT 状态请求那个旧地址，本服务器会 ACK 一个与接收端**不同网段**的 IP；客户端认为租约有效而长期不再重新请求 → "拿到了 IP 却连不上"，用户反复重试。正确做法是回 **DHCPNAK**，客户端立即回 INIT 重新 DISCOVER（秒级）。

附带：接收端启动 DHCP 前"只要没有 169.254 就等 20 秒 APIPA"——网线已连好且网卡已有 IP 时纯属白等（`control.py: _setup_target_dhcp`）。

### 修复
`dhcp_server.py`
- 新增 `_alloc_ip()`：跳过服务器自身与已分配地址（原先 option 50 占用的地址不会被 `_next_ip` 跳过 → 可能重复分配/冲突）。
- `_handle_request()` 改为返回 `(yiaddr, nak)`：option 50 请求的地址不属于本服务器网段 → 回 **DHCPNAK**（RFC 2131 行为）。
- 新增 `_send_reply()`：OFFER/ACK/NAK 从**监听 socket（0.0.0.0:67，源端口合规）+ 每个有线网卡出口 socket** 各发一份，每份重复 2 次抗丢包；目标端口优先用**客户端实际源端口**（回退 68），可兼容源端口非 68 的客户端。
- `_build_dhcp_packet(..., minimal=True)`：NAK 只带 option 53/54/56，不带租约/掩码/网关。

`control.py`
- `_setup_source_network`：重试窗口 60s → **300s**，退出条件增加 `not self._transferring`；**每轮 release+renew**，且 renew 放**后台线程**（用 `renew_idle` Event 防并发），主线程每 2 秒观察一次，拿到 `169.254.100.x` 立即结束。
- `_setup_target_dhcp`：只有**有线网卡完全没有 IP** 时才等 APIPA（原为"没有 169.254 就等 20 秒"）；网卡地址均不在 169.254/16 时打印明确警告。

### 测试
`tests/test_func.py` 新增 B4a~B4d：异网段 REQUEST → NAK / 同网段 REQUEST → ACK、地址池不重复分配（option 50 占用 .2 后新客户端拿 .3）、NAK 报文最小化、应答重复发送且目标端口用客户端实际源端口。
回归：`--only func` 39/39；`func + full_flow + ui + ui_readability + disconnect + user_cases` **153/153 通过**。

### 未做（可选增强）
彻底消除 Windows DHCP 客户端退避的做法是**源端自实现 DHCP 客户端**（自建 UDP 套接字每秒广播 DISCOVER → 收 OFFER → 发 REQUEST → 收 ACK，再用 `set_ip_via_netsh` 应用 IP），可把获取 IP 降到秒级；需要服务器把应答发到客户端实际源端口（已在本次修复中支持）以避免与系统 DHCP 服务抢占 68 端口。本次未实施。

## 根因定位：`Start-Process -Credential` 报"请求的操作需要提升"（Win32 740）

### 乱码还原（先解编码，再看内容）
报错原文是乱码 `ڳ´޷д: ĲҪ`。**这是解码方式造成的**：子进程输出是 GBK(cp936)，而代码用 `subprocess.run(..., text=True, encoding='utf-8', errors='ignore')` 读——GBK 字节里恰好构成合法 UTF-8 序列的部分被解出来、其余被丢弃，中文全丢只剩残渣。
还原办法：把候选中文按 `s.encode('gbk').decode('utf-8','ignore')` 比对即可确认（≈1/3 汉字能"幸存"）。
真实报错 = **`由于出现错误，无法运行此命令: 请求的操作需要提升。`**（= This command cannot be run due to the error: The requested operation requires elevation.）

### 根因
`Start-Process -Credential` 底层是 **`CreateProcessWithLogonW`**，该 API **无法创建提升(elevated)的进程**：UAC 开启时它只产生**被过滤的普通令牌(Medium IL)**。当目标安装包清单声明 `requireAdministrator`（QQ 等绝大多数安装包都是）时，创建直接失败并返回 **740 ERROR_ELEVATION_REQUIRED**。
关键结论：**调用方自己已经是管理员也修不好**——不是"调用方没提权"，而是该 API 天生不具备提升能力。
佐证：开发机 `EnableLUA = 0`（UAC 关闭）故不报错，故障只在 UAC 开启的目标机出现。

### 修复（`软件下载附件/install.py`）
1. **`_decode_console(raw) -> str`**：按 `utf-8 → gbk → mbcs` 依次尝试解码，取代写死的 `encoding='utf-8', errors='ignore'`。所有 `subprocess.run` 改为 `capture_output=True`（不加 text）后手动解码。
2. **`_log()`**：同时打印到控制台并追加写入 `install_debug.log`（`run_server()` 启动时清空）；模块级 `DEBUG = True` 为总开关。
3. **`_log_startup_banner()`**：启动即打印 python 路径/版本、脚本目录、当前用户、`IsUserAnAdmin()`、UAC 注册表（EnableLUA / ConsentPromptBehaviorAdmin / FilterAdministratorToken / PromptOnSecureDesktop / EnableInstallerDetection）。
4. **`_collect_diagnostics(exe, args)`**：安装前打印目标程序存在性与大小、`net user <account>` 全文、是否在 Administrators 组、`query user` 登录会话列表。
5. **`run_installer_as_lingtong` 改为 4 种方式依次尝试，首个成功即返回**：
   - **方式 0 `_launch_directly`**：当前进程已提升 **且** 当前用户就是目标账号 → 直接 `Popen(..., DETACHED_PROCESS)`（同会话、界面可见、无 UAC 弹窗）。
   - **方式 1 `_launch_via_scheduled_task`**：`schtasks /Create /SC ONCE /ST 00:00 /RL HIGHEST /RU <acct> /RP <pw> /F` + `/Run`。**这是唯一能真正提升的方式**——计划任务由任务计划服务(SYSTEM)用账户**完整令牌**启动，不受 UAC 过滤。细节：
     * 账号有交互式会话时加 **`/IT`**（否则跑在会话 0，安装界面不可见）；带 `/IT` 创建失败会自动去掉 `/IT` 重试。
     * `/Query /FO LIST /V` 抓「上次运行结果 / 要运行的任务」写入日志；**Last Result == 0x41303（从未运行）判为失败**并交给后续方式兜底。
     * 任务名 `LingtongInstall_<pid>_<seq>` 唯一；启动 15s 后 `Timer` 删除（不影响已拉起的进程）。
   - **方式 2 `_launch_with_createprocesswithlogonw`**：ctypes 直调 advapi32，**拿原始 Win32 错误码**（已实测：错误账号返回 1326）。附 `_WIN32_ERR_HINTS` 映射 740/1326/1327/1385/1907/1909/1789 等。

## 纠正：撤销 install.py 的 UAC 提权方案，回归"后台以 lingtong 身份静默安装"

### 用户反馈（2026-09-10，态度很明确）
1. **不该申请 UAC 提权** —— lingtong 本身就是本地管理员账户，直接用它的身份启动安装程序就行。

3. **加了自提权后程序反复请求系统授权、反复运行**。
4. 架构是：**下载服务由用户（当前登录用户）运行，安装由 lingtong 身份运行**。

### 第 3 条是我引入的真实 bug（已回滚）
`Boot_Software_Install.cmd` 里用 `net session >nul 2>&1` 判断是否已提权：**Server 服务未启动时，即使进程已经是管理员，`net session` 也返回非 0** → 脚本再次 `Start-Process -Verb RunAs` 重开自己 → 又判断失败 → **无限递归重启 + 反复弹 UAC**。自提权代码已整段删除，`Boot_Software_Install.cmd` 恢复原样（只剩 `start python` + `start 浏览器`）。

### 已删除的方案（不要再加回来）
- `_launch_directly`（方式零，依赖"当前进程已提升"）
- `_launch_via_scheduled_task`（方式一，`schtasks /RL HIGHEST`）—— 创建"以其他用户 + 最高权限"的计划任务必须由**已提升**进程发起，与"下载服务由普通用户运行"的架构直接矛盾；`_has_interactive_session` / `_current_user_name` / `_TASK_SEQ` / `_TASK_LOCK` / 顶层 `import re` / `import threading` 一并移除。

### 现在的实现（`run_installer_as_lingtong`）
只保留一条主路径 + 一条回退，**全程不弹任何窗口、不等待安装结束**：
1. `ctypes` 直调 `advapi32.CreateProcessWithLogonW`（`_launch_with_createprocesswithlogonw`）—— 首选，后台静默、无中间进程、返回原始 Win32 错误码
2. PowerShell `Start-Process -Credential`（`_launch_via_powershell_credential`）—— 同一 API，仅作回退对照

`_collect_diagnostics` 措辞也改了：不再要求"让 cmd 以管理员身份运行"，改为"安装将以 lingtong 身份后台静默运行，不弹 UAC、不弹任何确认框"，并把"本进程是否已提升"标注为**与安装身份无关的参考信息**。

### 740 怎么办（关键结论，别再走弯路）
`CreateProcessWithLogonW` 在 UAC 开启时只能产生**被过滤的普通令牌(Medium IL)**，遇到清单声明 `requireAdministrator` 的安装包必然返回 740，**调用方是管理员也没用**（API 固有缺陷）。能在**不弹窗**前提下解决的办法只有**预先配置目标机**：
- 关闭 UAC（`EnableLUA=0`）；或
- 让 lingtong 就是**内置 Administrator（RID 500）**——`FilterAdministratorToken=0`（默认值）时该账户不受令牌过滤。

开发机实测 `EnableLUA=0`、`FilterAdministratorToken=1`，所以本机不会复现 740；故障只在 UAC 开启的目标机出现。**不要在运行时用弹窗/提权去"解决"它。**

## 第七轮：用户点明运行账户不是管理员 → 方式三改成两段式（2026-09-10）

**用户补充的关键事实**：`D10460_chenzhiyu` 与后期运行本程序的用户，**都只隶属于 Users / Power Users**。

**但这条信息反而指出了解法**——问题不在"用哪个 API 提权"，而在"**由谁发起**"：

```

        └─ lingtong 进程(deny_only 管理员)

```

**已实现改动（`install.py`）**：
- `_launch_via_scheduled_task` 重写为两段式：不再在本进程跑 schtasks，而是把 `schtasks /create && /run` 拼成 `cmd /c (...)`，用 `_cpwl_once` 以 lingtong 身份执行；lingtong 侧输出重定向到 `F:/Appl/Installers/lingtong_elevate.log` 以便看到真因。
- 失败时用 `_run_as_lingtong` 请 lingtong 删掉残留任务（当前账户没有删别人任务的权限）。
