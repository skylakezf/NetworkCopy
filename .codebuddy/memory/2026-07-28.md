## 全项目 Bug 审查 + 改进调研（未改代码，仅报告）

### 致命 Bug（当前主流程无法工作）
1. control.py 与 file_transfer.py 接口脱节：
   - `FileServer(...)` 未传 auth_code / cert_paths → ssl_ctx=None → `get_request` 抛 RuntimeError，服务器拒绝所有连接；auth_code="" → 所有请求 403。
   - `download_files` / `scan_source_device` 未传 auth_code → ping 403 → "无法连接源设备"。
   - control.py 完全没有生成/显示/输入验证码的逻辑（tls_utils 未被 control 引用）。
2. `_send_json` (HTTP/1.1 keep-alive) 未发送 Content-Length → 客户端 /ping /list read() 挂起直到超时 → JSON 端点全部失败。
3. `_download_batch` 4 处 except 分支 `for rel_path, fsize, target_path in remaining_tasks` 解包 3 值，但元素是 4 元组 (含 mtime) → ValueError。
4. verifier.py `_retry_missing_files` / `_download_one_file` 用 http:// 明文 + 无 pwd → 服务器 TLS+403 必然失败。
5. control.py `run_verification` 未传 server_ip / gtmc_new_name → 重试下载永不触发；且源端已把 GTMC_User_Profiles 重命名为带日期后缀，CSV 未 patch → 该目录全部误报 N。

### 其它 Bug
- `_resolve_path` 路径穿越：normpath 后 "..\\.." 前缀未拦截。
- nic_scanner `_format_speed` Gbps 分支输出 "1.0GbpsGbps"（rstrip 后又拼 "Gbps"）。
- netsh 回退：列表参数里又加了引号 `f'"{desc}"'`，且传的是 Description 而非连接名 → netsh 必失败。
- UI 设备下拉框选择的 IP 未被使用，`_connect_and_download` 硬编码 DHCP_ASSIGNED_IP=169.254.100.2；DHCP 首租约被他机抢走时连错设备。
- `_pause_event.clear(); wait()` 无人 set → "pause" 会死锁（当前死代码）。
- progress_reporter 线程在有 errors 时永不退出（completed<total）。
- dhcp_server `wait_for_client` docstring 说返回 (success, ip) 实际返回 bool。
- JSON 用 utf-8-sig 编码（带 BOM，违反 RFC 8259）。
- ip_config SOURCE_IP/TARGET_IP 语义与 control.py 实际角色相反（易误用）。

### 改进方案（调研结论）
- JSON 响应补 Content-Length（或 Connection: close）。
- 大量小文件：改用 tarfile 流式打包 over HTTPS（server 边 walk 边写 wfile，client 边收边解包），替代自制 batch 二进制协议，减少往返。
- 大文件断点续传：HTTP Range。
- 写文件用临时文件 + os.replace 原子替换。
- 校验增加流式 zlib.crc32（比仅 size 可靠，比 MD5 快）。
- MEMORY.md 已更新：端口实为 9999（非 443/80）。

## 分区检测 + 按钮分离修复（已完成，py_compile + 实测通过）

### 1. 分区检测/自动映射失效（"检测到0个可用分区"）
- 根因：disk_scanner.py `get_partition_drive_mapping` 解析 `VOLUME_DISK_EXTENTS` 时结构偏移错误。
  - `VOLUME_DISK_EXTENTS` 在 `NumberOfDiskExtents`(4字节) 之后有 4 字节对齐填充，首盘区从 offset **8** 开始（非 4）。
  - 每个 `DISK_EXTENT`：`DiskNumber` 在相对 offset 0，`StartingOffset`(LARGE_INTEGER) 在相对 offset **8**（前面 4 字节 DiskNumber + 4 字节对齐填充），非 4。
- 原代码 `ext_offset = 4 + ei*24` 且 `StartingOffset` 读 `ext_offset+4` → 每个卷的 ext_start 恒为 0 → 与分区偏移匹配失败 → 映射返回 {} → 自动填充 0 个、按钮不自动点亮。
- 修正：`ext_offset = 8 + ei*24`，`DiskNumber` 读 `ext_offset+0`，`StartingOffset` 读 `ext_offset+8`。实测 PhysicalDrive0 现在返回 `{3:'C',4:'D',5:'E',6:'F'}`，count=4。
- 附带改进 control.py `_auto_fill_drive_mapping`：优先同名盘符匹配（源 D→目标 D），否则按序跳过首个系统分区补齐；调用处改为传完整 part_map。

## 自动映射改为按物理分区顺序（已完成，py_compile + 实测通过）
- 用户规则：盘符可能乱序（4 分区物理序 CDEF 可能挂载为 CEFG；3 分区机械盘可能挂载为 EDF），映射必须按分区在磁盘上的物理顺序，兼容 GPT/MBR。
- disk_scanner.py：新增 `get_partition_details(disk_number) -> [(starting_offset, part_number, letter), ...]`，按 StartingOffset 排序（MBR 逻辑分区号不连续，故不用分区号排序）；`get_partition_drive_mapping` 改为其 wrapper；函数内早退分支 `return {}` 全部改 `return []`。
- control.py `_auto_fill_drive_mapping(ordered_letters, ntfs_count)` 重写：
  1. 输入为物理顺序盘符列表；2. 去掉盘符 C（系统分区）；3. 剩余 >3 个则从头部跳过（视为系统/保留分区）；4. 按物理顺序依次填充 D→E→F。
  - 例：C,E,F,G → D=E, E=F, F=G；三分区 E,D,F（物理序）→ D=E, E=D, F=F。
- `_on_disk_selected` 调用处改为 `get_partition_details` 并传物理顺序盘符列表。
- 实测 PhysicalDrive0：details=[(offset,3,'C'),(...,4,'D'),(...,5,'E'),(...,6,'F')]，wrapper map 输出不变。
