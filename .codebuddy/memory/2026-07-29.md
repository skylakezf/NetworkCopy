## 发送端报错 "读取握手头失败/超时" 的定位与修复
- 用户贴出源端（发送端文件服务器）日志：`[诊断] 收到新连接来自 ('169.254.116.119', xxxx)` + `拒绝连接 ... 读取握手头失败/超时 (按明文处理)`。注意 `按明文处理` 是**旧版 exe 才有的文案**；当前源码 `get_request`（file_transfer.py ThreadingFileServer）已经正确用 `self.ssl_ctx.wrap_socket(conn, server_side=True)` 完成 TLS 握手（约 line 377），不会"按明文处理"。
- 真正的触发源：接收端 `_connect_and_download` 里的 **TCP 端口探测**（`socket.create_connection` 连上后立即 `close()`，不发任何数据）。Windows 上这种"连上就关"会产生 RST，源端 `get_request` 的 `recv(2, MSG_PEEK)` 读到 RST → 抛异常 → 误报"读取握手头失败/超时"。该探测连接本就不发 TLS ClientHello，故必然被当作非法明文拒绝；但这是探测连接，真正的下载连接（HTTPS/TLS）是另一条，理论上不受影响。日志吓人且误导。
- 已修复（control.py）：把接收端裸 TCP 探测改为**真实 TLS 握手探测**（`ssl.wrap_socket(create_connection(...), server_side=False, context=ssl._create_unverified_context())`，握手成功后 `settimeout(None)` 再 `close()`）。好处：① 干净验证 TCP+TLS 是否真通；② 源端看到合法 ClientHello 正常完成握手、不再误报拒绝；③ 若源端是旧版 exe（未完成 TLS 握手），探测会明确报 "TLS 握手失败" 提示重新打包。日志变成"[诊断] TLS 端口 x:x 可达 (TCP+TLS 握手成功)"。
- 顺带加固（file_transfer.py）：TLS 握手成功后 `conn.settimeout(None)`，取消握手期 30s 超时，避免大文件传输期间因空闲间隙被服务端超时断开。
- 关键结论：**用户若跑的是 dist/*.exe（旧构建），必须重新打包（build.bat）**。旧构建的 `get_request` 没有 wrap TLS，握手永远完成不了，传输必然失败；当前源码已正确 wrap，从 `python main.py` 跑源码即可验证。
- 验证：`py_compile control.py file_transfer.py ip_config.py dhcp_server.py verifier.py` 通过。

## 目录无写入权限导致 PermissionError 崩溃修复（两轮迭代）
- 第一轮：仅 catch PermissionError，不够。`os.makedirs(d, exist_ok=True)` 遇到路径已存在为**文件**（非目录）时仍抛 `FileExistsError`（如 `Contacts` 在源端用户目录下是文件），导致下一轮崩溃。
- 第二轮（最终方案）：三段式预检：
  1. `os.path.isfile(d)` → 路径是文件 → 直接跳过（无法创建同名目录）
  2. `os.path.isdir(d)` → 目录已存在 → `os.access(d, os.W_OK)` 检查可写性 → 可写则跳过创建，不可写则记入跳过
  3. 路径不存在 → `os.makedirs(d, exist_ok=True)` → catch `(PermissionError, FileExistsError, OSError)` → 失败则跳过
- 跳过目录对应的文件在后续分组阶段过滤，并从 `partition_total` 扣除。

## 网络传输性能优化（用户反馈 1GB≈3min 太慢，900Mbps 网卡）
- 诊断：1GB 在 900Mbps 链路上理论 ~9s，实际 ~180s（5.7MB/s，20x 慢）。4 处修复：
  1. **服务端 `wbufsize`**: 从默认 0（无缓冲，每个 write 直通 socket → TLS 拆成 16KB 片逐个发包）改为 1MB（BufferedWriter 合并写入），大幅减少 SSL/TLS 记录碎片和 TCP 分段
  2. **客户端 `TCP_NODELAY`**: 新增设置，禁用 Nagle 算法，防止延迟 ACK 拖慢服务端发送节奏
  3. **客户端 `SO_RCVBUF`**: 新增 2MB 接收窗口，匹配服务端 `SO_SNDBUF=2MB`。Windows 默认仅 64KB，严重限制 TCP 吞吐量
  4. **Chunk size 1MB→4MB**: 减少循环次数和 TLS 记录打包开销。服务端末块追加 `flush()` 确保缓冲数据立即推送。同步修改服务端 _send_file 和客户端 download_single
- 验证: `py_compile file_transfer.py` 通过

## 服务端线程爆炸导致 ConnectionReset/Timeout 崩溃修复（用户反馈 E 盘 ~1W 文件后报 WinError 10054/10060）
- 错误模式：先 `10054`（远程主机强迫关闭连接）→ 后 `10060`（超时），说明源端服务器资源耗尽。
- 根因：`ThreadingMixIn` 无线程数上限，客户端 8 worker × 上万文件请求 → 服务端创建/销毁数万个线程 → 最终 OS 拒绝新连接。
- 修复 5 处：
  1. **服务端** `ThreadingFileServer`: 新增 `BoundedSemaphore(MAX_CONCURRENT_HANDLERS=16)`，`process_request` 先 acquire 再 super，限制最大并发处理线程数
  2. **客户端** `DEFAULT_DOWNLOAD_WORKERS` 8→4：减少对服务端的并发连接压力
  3. **重试逻辑**: `_download_single_file` 和 `_download_batch` 的连接异常现在 `raise` 重新抛出；新增 `_download_single_file_with_retry` 和 `_download_batch_with_retry` 包装器，连接错误时指数退避重试（0.5s/1s/2s，最多 3 次）
  4. **ThreadPoolExecutor 改用 retry 包装器**：单文件任务改用 `_download_single_file_with_retry`，批次任务改用 `_download_batch_with_retry`
  5. **分区间关闭连接**: `download_files` 每个分区完成(含被取消)后调用 `_close_all_thread_connections()` 清理当前线程的持久连接，防止僵死连接跨分区复用
- 验证: `py_compile file_transfer.py` 通过

## 异常退出时后台进程一并关闭（用户要求：异常退出时后台进程也需退出）
- 问题：窗口关闭 / 异常崩溃时，FileServer 线程（HTTPS serve_forever）和 DHCP 服务器线程（UDP 循环）可能未正确释放端口和资源，系统休眠策略也可能未恢复。
- 双重保险机制：
  1. **`WM_DELETE_WINDOW` 协议**（main.py）：点击窗口 X 按钮时触发 `_on_close()` → `controller.shutdown()` → `app.destroy()`
  2. **`atexit.register` 兜底**（main.py）：即使不走窗口关闭流程（异常传播到顶层 / 进程退出），atexit 回调也会执行 `controller.shutdown()`
- `Controller.shutdown()` 方法（control.py）按顺序清理：
  1. 停止校验线程（`_stop_verify=True` + `join(timeout=3)`）
  2. 停止文件服务器（`_file_server.stop()` → 释放 HTTPS 端口 + 线程）
  3. 停止 DHCP 服务器（`_dhcp_server.stop()` → 释放 UDP 端口 + socket）

## 校验重试卡死修复（用户反馈：重新下载权限问题跳过的文件时，重试3次后卡住、网卡利用率为0）
- 根因：`_retry_missing_files` 中 `resp.read()` 在 HTTP/1.1 下如果服务端 Content-Length 与实际发送字节数不匹配（服务端线程崩溃 / 网络中断 / 缓冲区未刷），客户端会**无限阻塞**等待剩余字节。`urlopen(timeout=120)` 在 TCP 连接建立后，`read()` 阶段不总是受 timeout 约束。
- 修复（verifier.py）：
  1. **`socket.setdefaulttimeout(60)` 兜底**：在 `_retry_missing_files` 入口设置 socket 默认超时 60s，finally 恢复原值。这样 resp.read() 即使阻塞也会在 60s 后抛 socket.timeout。
  2. **批量请求连接重试（3次）**：batch 请求包装在 3 次重试循环中，`URLError/ConnectionError/TimeoutError` 时指数退避（0.5s/1s/2s），3次都失败才回退逐个下载。
  3. **`Connection: close` 头**：批量请求 Header 显式加 `Connection: close`，避免 HTTP/1.1 keep-alive 竞态导致连接僵死。
  4. **预检查跳过已知无权限目录**：收集 CSV 中 N 文件时，对父目录做预创建尝试。若 `os.makedirs` 抛 `PermissionError/FileExistsError/OSError`，将该目录加入 `_skipped_parents` 集合，跳过该目录下所有文件（与首次下载跳过的目录一致），避免反复尝试已知无法写入的位置。
  5. **`_download_one_file` → `_download_one_file_with_retry`**：回退逐个下载时改用带 3 次连接重试的版本（原版无重试），`_download_one_file` 保留为兼容包装器。
  6. **`os.makedirs` 预判保护**：批量响应解析写入前，先 `isdir` 检查+尝试 `makedirs`，失败则跳过该文件而非静默 hang 在磁盘操作上。
  7. **`_retry_missing_files` 拆为 wrapper+inner**：wrapper 负责 socket timeout 的 set/restore，inner 负责业务逻辑，确保异常路径也能恢复 socket 超时设置。
