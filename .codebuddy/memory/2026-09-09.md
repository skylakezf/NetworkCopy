## BUG 修复：含逗号文件名被校验误判 + 重复下载出 0KB 垃圾文件（重要）

### 症状（用户报告 10 个文件）
传输成功（正确文件在），但同目录多出一个 0KB、标点被改写的文件；校验报告判失败。共同点：文件名含逗号。

### 根因链（3 环叠加）
1. `verifier.run_verification` **无条件**调 `_repair_csv_in_place()` → 该函数把 CSV 全角逗号「，」一律替换为半角「,」（为兼容旧版 `escape_csv` 的历史 bug）。中文输入法下文件名本就含全角逗号，属极常见 → **正确 CSV 路径被改坏**。
2. 校验按改坏的路径 `os.path.isfile` → False → 标记 N「文件不存在」。
3. `_retry_missing_files_inner` 重试下载：**不检查 data_len==0**，服务端找不到文件返回空占位（file_transfer.py:584 注释明确"空 data 代表服务端跳过"），客户端照写 `open(target_path,"wb")` → 落 0KB 垃圾文件。
   - 对比：主传输 `file_transfer._download_batch` 有 data_len==0 + 大小校验 + tmp+rename 保护，所以只有**重试下载**这条路径会产出 0KB 文件。

### 修复（verifier.py）
- 新增 `_csv_path_candidates` / `_csv_path_to_disk` / `_disk_exists_for_csv_path` / `_resolve_csv_field` / `_has_comma`。
- `_repair_csv_in_place(csv_path, log, partition_map=None)`：只在「原路径磁盘不存在 + 候选路径存在」时改写，且**只改 FullPath**（FileName 无法验证，不动）；无 partition_map 时直接返回 0 不修改。候选含**双向**（全角→半角 修旧 bug；半角→全角 修被本 bug 改坏的历史 CSV）。
- `run_verification` 调用处传 `partition_map=partition_map`。
- `_verify_single_row` / `_retry_missing_files_inner`：路径不存在时先试标点变体再判缺失。
- 重试下载：data_len==0 且 expected_size!=0 → 不写；大小不符 → 不写；改 tmp+rename。
- `_download_one_file_with_retry` 新增 `expected_size` 参数，同样 tmp+校验+rename，杜绝 0KB。
- `calc_allocation_migration.escape_csv`：`rstrip()` → `rstrip("\\")`（避免去掉文件名尾部空格导致路径失真）。

## 小文件打包优化（用户选方案1折中：放宽包上限，不加压缩）

### 问题澄清
`/batch_get` 是**拼包零压缩**（响应=二进制帧 path_len|path|data_len|data），不存在 zip/压缩比。用户以为"小文件包太小拖慢"的真正瓶颈：**每包固定开销(HTTPS 往返/HTTP头/服务端逐文件处理)×包数量**。原 `BATCH_MAX_FILES=200` 时 5 万个 <1KB 文件(内容仅~25MB)被切 250 个包、每包载荷仅~100KB。

### 落地改动（file_transfer.py，仅常量）
- `BATCH_MAX_FILES`: 200 → **5000**（主收益来源）
- `BATCH_MAX_TOTAL`: 20MB → **100MB**
- `BATCH_MAX_PATH_BYTES`: 512KB → **3MB**
- 服务端 `/batch_get` 请求体上限: 2MB → **4MB**（含注释，配套路径预算留转义余量）
- 折中方案的已知代价（用户已确认接受）：两端仍整包读内存，100MB 级包 × 4 worker 并发峰值数百 MB~1GB，小内存 PE 机有 OOM 风险；网络级失败整包重传 100MB；首字节延迟变大。若将来要更大包 → 应两端改流式边读边写，而非继续调大上限。

### 压缩判断（用户授权 AI 决定）
本轮**不加压缩**。理由：① 拼包已把几万文件降到~10包，数据量在 100M 级时千兆网传输<1s，压缩省的是链路字节，收益低且耗 CPU；② 文本/配置类小文件占比小，需魔数/扩展名判断 + 协议加标志位，与"改动极小"折中目标冲突；③ 若未来出现单分区>1GB 纯文本工程/文档场景，再做"按包类型 deflate"更划算。

## 按空闲内存自适应单包内容上限（用户提出动态分配；已实现）

### 用户给出的映射规律（已采纳）
空闲内存÷8 → 512/768/1024MB → 64/96/128MB。实现为 `_recommended_batch_total_mb()`：`clamp(空闲MB÷8, 32, 128)`。

### 机制（关键认知）
`/batch_get` 两端各 hold ≈ 单包内容内存（发送端整包读入构造响应、接收端整包读入解析），因此：
- 发送端(FileServer) `/ping` 响应新增字段 **`batch_max_total_mb`** 通告自身建议；
- 接收端 `_download_files_inner` 连接成功后（复用既有 /ping 循环拿到的 data，零额外请求）读取该字段 + 本地探测值，**取 min** 作为本次传输 `batch_total_limit`，替代静态 `BATCH_MAX_TOTAL` 参与分批（分批判断 L2100 区改用 `batch_total_limit`）；
- 传输期间仅探测一次（开头）。

### 新增函数（file_transfer.py）
- `_get_avail_phys_mb()`：ctypes `GlobalMemoryStatusEx`（PE 无 psutil；非 Windows/失败返回 None）。
- `_recommended_batch_total_mb(avail_mb)`：档位映射 + 32~128 clamp；空值返回 None。
- 为消静态告警，inner 开头补 `data = None` 初始化。

### 安全兜底（不影响用户正常使用）
任一侧探测失败/旧版服务端(无字段) → 回退常量 `BATCH_MAX_TOTAL`（现为 64MB，语义变为"回退默认"而非实际生效值）。
